# Перевірка RWB1 handover — 19.10.2026

Перевірено локальний handover іншого агента, три Python-скрипти та наявні JSON/JSONL логи. Скрипти ARP-poisoning не запускались; оригінальні файли й логи не змінювалися і не копіювалися до Git. Додатково виконано 40-секундний read-only захват MQTT на OpenWrt через SSH; сирий потік оброблявся лише в пам’яті. HTTP-сторінка адаптера не запитувалася.

## Підтверджено

- У JSONL є 34 записи PUBLISH у напрямку адаптер → брокер. З них 32 payload можна прочитати як окремий JSON, а два містять дані, які цей parser не представляє як один JSON.
- В усіх 32 розібраних полях `b.co` Base64 декодується у 7 байтів: slave 5, function 3, byte count 2, word, CRC. **32/32 проходять стандартний Modbus CRC16**, CRC-байти little-endian. Зайвого початкового `00` у цих кадрах немає.
- 34 записи утворюють 17 пар із однаковими напрямком, IP/портами та MQTT body. Різниця часу в парі — приблизно 0,026–0,148 мс. Це повторні спостереження, а не 34 незалежні виміри. У логу немає TCP sequence, щоб остаточно розрізнити дублювання захвату й повторну передачу.
- Логи містять raw unsigned values, зокрема `47105`. Без request/register map одиниці невідомі; ці числа не можна автоматично позначати W або підставляти у PV/grid/battery/load.
- У новому router capture є двосторонній обмін: PUBLISH адаптер → брокер (408 байтів JSON payload) і PUBLISH брокер → адаптер (53 байти). Перше повідомлення містить **CRC-валідні FC03 блоки на 1, 8, 21 і 29 регістрів**. Твердження «передається лише один регістр» не відповідає цьому спостереженню. Валідних FC03 read requests з адресою регістру в цьому 40-секундному вікні не знайдено.

## Виправлено у власному аналізаторі

Попередній `inspect_rwb1_mqtt_capture.py` шукав тільки responses на 21/45 слів і Base64 рядки довжиною від 60 символів. Тому висновок «немає Modbus» для коротких 87/94-byte JSON повідомлень був надто сильним: однослівні відповіді не входили у пошук.

Тепер знаходяться CRC-валідні FC03 replies на 1..125 слів у raw, hex і Base64. Окремо розпізнаються CRC-валідні read requests та виводяться лише register/count. Короткі й інші непрофільовані блоки не отримують вигаданих одиниць або призначення. Модуль декодування 21-word candidate для сенсорів зберіг суворі вимоги й не приймає коротких кадрів.

Цільові перевірки: **38/38 PASS** (6 modules); повний runner на цьому етапі не запускався. Production coordinator і живі сенсори ще не використовують ці зміни.

## Проблеми отриманих скриптів

- ARP poisoning активно змінює gateway mapping на адаптері. Це не пасивний sniff. Scripts не містять явного відновлення ARP після завершення.
- `mitm_duplex.py` підміняє ARP лише в одному напрямку. Назва duplex і фільтр на два напрямки не гарантують, що зворотний трафік потрапляє через Windows. Відсутність incoming MQTT у цьому JSONL не означає відсутності команд брокера.
- MQTT parser розбирає TCP payload як окремий MQTT packet без stream reassembly, не обмежує body значенням Remaining Length, урізає JSON до 400 символів. Це пояснює неповні/склеєні повідомлення й не дозволяє точно вимірювати каденцію за цим логом.
- `mitm_broker.py` очікує 8-byte reply з початковим `00`, тоді як наявні frames мають 7 bytes без такого prefix.
- Вибір `bytes.fromhex(co)` для будь-якого рядка парної довжини помилковий: коректний Base64 теж має парну довжину. Такі replies відкидаються до Modbus decoder.
- Publisher підключається до локального broker до виклику `start_broker()`. `127.0.0.1` на Windows не є localhost іншого HA host. Це не готова доставка в HA.
- Частота 2–5 секунд, одиниці W, прив’язка до окремих регістрів, назва ThingsBoard і призначення HTTP тільки для OTA не доведені цими файлами.

## Подальша робота

1. Спостерігати через роутер з TCP stream reassembly в обох напрямках, без ARP poisoning. Не дублювати однакові TCP bytes; розділяти reconnect sessions.
2. Зберігати у діагностиці лише безпечні метадані й форми blocks. Встановити, в яких JSON полях передаються 1/8/21/29-word blocks.
3. Знайти read request/config, який ідентифікує кожний блок, або незалежно перевірити карту регістрів. Час і схожість числа на потужність самі по собі не є достатньою атрибуцією.
4. Виміряти інтервал повного підтвердженого набору, з’ясувати, чи адаптер може опитувати інвертор незалежно від cloud. Пасивний tap ще не є cloud-independent транспортом.
5. Лише після цього ввімкнути перевірений provider у плагіні. Не замінювати наявні сенсори непозначеними raw words.

Специфікація FC03: https://www.modbus.org/file/secure/modbusprotocolspecification.pdf (розділи 4.2 і 6.3). У response немає starting register address; він міститься в request.
