# План реалізації локальної телеметрії

Уточнення scope 19.10.2026: див. [актуальний план гібридного режиму для Hermes](hybrid-telemetry-hermes-implementation-plan-2026-10-19.md). Поточний випуск — cloud за замовчуванням, opt-in пасивний RWB1 collector через сумісний роутер та окрема cloud history. Нижче збережено також попередні дослідницькі варіанти; вони не є вимогами цього випуску. Без сумісного роутера працює чинна хмара.

Дата: 19 жовтня 2026 року. Статус: реалізація розпочата; пасивний профіль RWB1 підтверджений п’ятьма полями на реальному кадрі, активне читання й доставка в HA ще не реалізовані.

Мета — додати у Smart Solar Inverter вибір джерела даних, щоб сумісні інвертори передавали телеметрію локально з перевіреною частотою. Наявні сутності, графіки та історія зберігаються. Для поточного комплекту спочатку перевіряємо PowMr POW-HVM6.2M-48V-N із Solar Plug-RWB1 типу 04, його Wi-Fi/LAN і мобільний застосунок. Користувач має OpenWrt, але не має окремого ESP32 або USB/RS232-перехідника. Загальний випуск також повинен мати реально перевірений спосіб без OpenWrt.

Цей план охоплює отримання, перевірку, підключення та налаштування телеметрії. Подальші зміни прогнозів і планувальників виконуються за [загальним планом покращень ШІ](telemetry-ai-roadmap-2026-10-19.md) після стабілізації даних. [Архітектура](local-telemetry-architecture.md) визначає межі інтеграції та необов’язкового шлюзу.

## Очікувана поведінка для користувача

Уточнений scope власника: RWB1 не змінюється; обрано read-only збирач на OpenWrt як додаткове джерело. Нижче описана цільова поведінка майстра; сам майстер і постійний collector ще не реалізовані.

У налаштуваннях інтеграції з’явиться пункт «Джерело даних»:

| Вибір | Поведінка |
| --- | --- |
| Хмара — типово | Поточний спосіб через обліковий запис виробника. Без router discovery, SSH, додаткового сервісу або запиту налаштувати роутер |
| Через роутер — додатково | Пріоритет перевіреним локально перехопленим readings; явна опція cloud fallback, видимий статус/свіжість джерела |

Майстер показує лише реалізовані сумісні способи, перевіряє з’єднання, відображає контрольні покази й зберігає налаштування в тій самій установці. Зміна IP або транспорту не створює другого комплекту сутностей. Роутерне перехоплення RWB1 поки залежить від його штатного cloud-з’єднання; хмарний акаунт/наявне встановлення зберігаються. Вимкнення telemetry fallback саме по собі не відключає cloud history чи cloud control і не є режимом повної незалежності від cloud.

Поточний маршрут: RWB1 → OpenWrt → штатна хмара; collector читає копію MQTT та передає її декодеру біля HA. ARP poisoning і перенаправлення призначення не потрібні. Користувачі без сумісного роутера продовжують cloud-only. Апаратні альтернативи лишаються поза поточним scope.

### Майстер додаткового підключення через роутер

1. Користувач відкриває налаштування чинної інтеграції та обирає «Через роутер». Інші користувачі цього кроку не бачать під час звичайного налаштування хмари.
2. Майстер пропонує знайдений router address або просить адресу. Разова авторизація виконується локально; дані доступу не потрапляють у діагностику. Перевіряються firmware, SSH host key, наявність capture tool і можливість читати потрібний інтерфейс.
3. До застосування показуються конкретні зміни на роутері, спосіб доступу з мінімальними потрібними правами та повернення до попереднього стану. Непідтримуваний роутер або відсутні права завершують майстер із поясненням, не ламаючи чинну інтеграцію.
4. Майстер вибирає пристрій і звіряє його зі стабільним inverter ID чинної config entry. IP не використовується як identity. Невідомий profile/register map не можна активувати як готове джерело.
5. Контрольна порція показує підтверджені SOC/PV/load та фактично виміряний інтервал оновлення. Збереження дозволяється після перевірки identity, decoder profile, CRC і fresh field coverage. Обіцянка 2–5 s без вимірювання заборонена.
6. Користувач бачить явну опцію «Якщо локальні дані недоступні — використовувати хмару». Якщо її вимкнено, втрачені покази стають unavailable; згода не підміняється навіть після помилки збереженої конфігурації.
7. Після збереження залишаються ті самі entities/історія. Статус показує активне джерело, вік даних і причину fallback; raw MQTT, теми і credentials у звичайному UI не показуються. Повторне підключення виконується автоматично.
8. Повернення на «Хмара» вимикає collector-підключення; зміна джерела не змінює Adaptive/Shadow/outage observation або право керувати інвертором. Для HEMS потрібна окрема перевірка достатності й часової узгодженості набору показів.

Реалізована основа `telemetry_sources.settings` і `TelemetrySourceRouter.from_settings`: без нової секції options дозволений лише cloud provider; неактивні collectors не опитуються навіть при помилці хмари. Після opt-in локальний provider отримує пріоритет, cloud fallback застосовується лише коли дозволений. Некоректна додаткова конфігурація не викликає startup exception, але повертає diagnostic issue. Підключення цих правил до production config flow/runtime ще не виконане.

Ізольований checkout оновлено до коміту `654a227`, основний checkout користувача не змінювався. Поточний цільовий набір: **47/47 PASS**, включно з cloud-default, opt-in та відмовами fallback. Це не підтверджує готовність майстра, collector або live deployment.

### Обмеження обладнання власника (19.10.2026)

У користувача є PowMr POW-HVM6.2M-48V-N, Solar Plug-RWB1 типу 04, мобільний застосунок і OpenWrt. Поточний scope — Wi-Fi/LAN, без BLE. Пізніша browser-перевірка користувача показала: GET `/` із явно наявним Basic Authorization для `<user>/<default-password>` повертає 404, а інший пароль — 401. Це сильна ознака прийняття `<user>/<default-password>`, але доступний захищений ресурс із 2xx ще не знайдено. Наступні досліди зосереджуються на доступному Wi-Fi/LAN трафіку та вже отриманих пасивних даних. Вони мають бути read-only: не перезапускати/переналаштовувати RWB1, не від’єднувати його від інвертора й не надсилати невідомі Modbus-запити.

Офіційний опис RWB1 заявляє BLE 5.0 для локальної діагностики та збору даних; опис Solar of Things у Google Play заявляє Bluetooth/local monitoring і сумісність із RWB1-04. Це робить BLE обґрунтованим майбутнім кандидатом, але не доводить, що GATT-сервіс відкритий для стороннього клієнта або доступний Home Assistant одночасно з телефоном. Публічної специфікації GATT/автентифікації поки не знайдено, а перевірити його на HA наразі неможливо через відсутність Bluetooth-адаптера. Спершу дослідити наявний Wi-Fi/LAN шлях; BLE повернути до плану лише як окрему необов’язкову гілку, коли з’явиться доступний адаптер. Не просити користувача надсилати пароль або токен.

## Експериментальний BLE-варіант (21.10.2026)

Реалізовано окремий версіонований read-only BLE-профіль RWB1
(`rwb1-ble-fee7-21w-le-v1`) з єдиним дозволеним Modbus read, суворою валідацією
конверта й фрагментації та інжектованим HA BLE transport. Це **експеримент,
opt-in**: coordinator, наявні сутності, історія та cloud-налаштування не змінені.
Рівень доказу — 2 успішні читання; фізична звірка з дисплеєм не завершена,
`battery_soc` і `load_power` лишаються діагностичними кандидатами, стабільність
30 хвилин / добу не перевірена, `battery_current` не підтверджено.
Подробиці: [rwb1-ble-experimental.md](rwb1-ble-experimental.md).

## Початковий стан

- Є автономний пакет `telemetry_sources` із моделями, вибором значень по полях, HA-entity provider, transport-neutral router і експериментальними RWB1/serial декодерами. Він не підключений до coordinator або config flow.
- Пасивне спостереження RWB1 містить CRC-валідну Modbus-відповідь із 21 словом. П’ять декодованих полів (`grid_voltage`, `battery_voltage`, `battery_soc`, `pv_power`, `load_power`) збіглися з історією HA в найближчому записі через секунду.
- Нове пасивне захоплення 19.10.2026 показало `little-endian` порядок слів: один кадр у 120-секундному вікні збігся з live HA за всіма п’ятьма полями — grid 234,3 В; PV 15 Вт; батарея 53,2 В і 90%; load 982 Вт. `big-endian` для того самого кадру дає фізично неможливі значення. Попередня примітка про big-endian була помилковою; п’ять старих збігів без збережених байтів не були доказом порядку байтів.
- Відкритий `powmr_comm` reference включає `POW-HVM6.2M-48V` у список моделей, що очікувано працюють, але його явно перевірені моделі не включають цю точну модель. Він описує Modbus RTU, slave 5, 2400 baud та читання 45 регістрів від 4501 (а також інший блок). Це сильний serial-кандидат для стендової перевірки, не доказ сумісності нашого пристрою.
- Незалежний ESPHome-проєкт Solar Plug підтверджує архітектуру read-only заміни RWB1 на сумісних HPVINV02-пристроях, але його фізичне підтвердження наведено для `POW-HVM6.2KP`, не `POW-HVM6.2M-48V-N`. Він вимагає від’єднати RWB1: два активні master одночасно на одному RS232 порту не підключаються.
- Додатково знайдено Solar2MQTT: проєкт має підтримку Home Assistant і MQTT та користувацькі повідомлення про роботу саме `POW-HVM6.2M-48V-N` через RS232 з ESP32/Max3232. Це сильніший практичний кандидат для маршруту без OpenWrt, але список має позначку user-reported/working-device, а не незалежний тест на нашому інверторі.
- Попереднє формулювання про підтверджену частоту 2–5 секунд було неточним. Пасивний capture дав один кадр у 120 секундах, а наступні 180- і 120-секундні вікна — жодного. Це може відображати нерегулярну публікацію, фільтрацію або стан каналу; виміряної частоти локального джерела поки немає.
- Запит `0x1195/21` не спостерігався в тому самому вікні, тому Modbus-відповідь не доводить адресу початку регістрів і не дає підстав генерувати запити. Поточні unit-тести використовують синтетичні кадри; реальні байти не збережені у репозиторії.
- Попередній висновок «`<user>/<default-password>` не підійшов» відкликаний: користувач показав 404 із цією парою і 401 з іншим паролем. Тіло 404 — короткий HTML `web error`, без посилань. Потрібно визначити реальні HTTP routes; відсутність `/` не доводить відсутності інших API.
- Локальна робоча копія відстає від поточної розробки й live. Підключати зміни до старого coordinator до звірки версій не можна.

## Етап 1 Узгодити код і довести профіль даних

1. Звірити локальний checkout, актуальний `develop` і manifest live-файлів. Перенести автономні зміни на актуальну базу у відокремленому робочому каталозі, зберігши незакомічені файли користувача.
2. Перевірити `models.py`, `selection.py`, `rwb1.py` щодо одиниць, часових міток, джерела кожного поля, невідомих значень та прив’язки до пристрою.
3. Зафіксувати provenance уже звірених п’яти полів. Підготувати тест реального кадру лише у тимчасовій пам’яті; не зберігати домашню телеметрію у відкритому репозиторії. Для подальших регресій використовувати синтетичні кадри.
4. Винести адресу пристрою, карту полів, порядок байтів та допустимі операції у версійований профіль моделі/прошивки. Не вважати всі RWB1 або всі моделі PowMr однаковими.
5. Перевірити CRC, помилкову адресу/функцію/регістр, нульові та відсутні значення, часові пояси й ізоляцію двох інверторів.

**Готовність:** пасивний кадр уже підтвердив одиниці й п’ять показів. До закриття Етапу 1 лишається перевірити суворі межі декодера й зафіксувати контрольний тест без збереження реальної телеметрії. Активне адресоване читання та частота залишаються окремими етапами; керування не змінюється.

## Етап 2 Підготувати ізольований RWB1 шлюз

1. Реалізувати або адаптувати із перевіркою ліцензії мінімальний сервіс, який зберігає потік RWB1 ↔ хмара та видає очищені спостереження плагіну. Початковий режим — без додаткових запитів до інвертора.
2. Обробити фрагментацію TCP, кілька MQTT-пакетів у одному читанні, перепідключення, обмеження розміру, NUL-префікс JSON, Base64 та CRC. Ключі сесій і private envelope не потрапляють у журнали.
3. Вести контекст запитів по пристроях/сесіях. Modbus-відповідь не містить початкового регістра: одного переданого в декодер запиту недостатньо для доведення кореляції. За конкуренції однакових блоків відповідь позначається неоднозначною й не публікується як достовірна телеметрія. Локальні читання серіалізуються та не заважають хмарним запитам.
4. Обмежити локальну ін’єкцію дозволеним читанням підтвердженого блока. Команди хмарного застосунку прозоро передаються наявним шляхом; шлюз не створює другого алгоритму керування.
5. Для першого прототипу використати наявний MQTT-брокер: окремі права/топіки для пристрою, схема повідомлення з версією, session/sequence, часом отримання, походженням і якістю полів. Retained-пакет або повторна доставка не стають новим виміром.
6. Підготувати конкретне правило маршрутизації лише для потрібного адаптера та його хмарного з’єднання. Перевірити зворотний маршрут у тій самій LAN, початковий listener і відновлення маршруту. Перед вимкненням шлюзу повертається початковий маршрут; відмова шлюзу має запускати перевірене відновлення, щоб не залишати адаптер без хмари.

**Готовність:** транспортні тести відтворюють розриви й фрагментацію; пасивний шлюз зберігає роботу хмарного застосунку; повернення маршруту перевірене на конкретній схемі. Немає додаткових записів налаштувань інвертора.

## Етап 3 Підтвердити адресований запит і частоту

1. Для RWB1 окремо підтвердити кореляцію вже спостереженого 21-словного кадру. Для прямого serial кандидата документація описує запит `0x1195/45`. Не змішувати профілі та не запускати прискорене опитування до перевірки саме на POW-HVM6.2M-48V-N.
2. Поступово перевірити інтервал 5 секунд, потім 2 секунди, якщо попередня перевірка не виявила помилок і пристрій дозволяє таку частоту. Налаштувати timeout, backoff та повернення до стабільної частоти.
3. Порівняти одночасно локальні покази, хмару, HA й доступні покази дисплея. Різницю часових міток між машинами не називати точною затримкою фізичного виміру.
4. Провести контроль щонайменше 30 хвилин, потім добове спостереження. Виміряти медіану/p95 інтервалів, успішність, пропуски, перепідключення та вплив на хмарний застосунок.

**Ціль приймання в стабільній LAN:** щонайменше 99% відповідей на дозволені читання та p95 інтервалу не більше подвійного обраного періоду. Це ціль перевірки, а не заявлена можливість обладнання. Якщо 2 секунди нестабільні, зберігається найшвидший доведений інтервал із конкретним поясненням. Час виміру залишається невідомим, якщо пристрій його не передає.

**Готовність:** зафіксовано підтверджений профіль, виміряний інтервал і відновлення після розриву. Нова телеметрія ще не підміняє production-сенсори.

## Етап 4 Підключити джерела до coordinator

1. Обгорнути поточне хмарне отримання в той самий контракт, зберігши чинну поведінку cloud-only. Додати постачальник локального шлюзу, його lifecycle та завершення при unload/reload.
2. Додати шар відповідності між канонічними назвами локальних полів і ключами `coordinator.data`. Зберегти масштаб, одиниці, знаки та наявні entity IDs.
3. Відокремити сталий ID інвертора від `api.device_sn` і доступності cloud API. Для наявної установки використати її поточний ID; у нової локальної установки застосувати перевірену ідентичність пристрою або створену сталу прив’язку, яку можна явно зіставити з хмарним пристроєм.
4. Реалізувати три політики: cloud-only, local-only, auto. В auto переходити по полях лише на придатні значення; не повертати старий кадр того самого джерела як свіжий після новішого невідомого значення без явної політики кешу. Перевіряти очікувані одиниці, забороняти не налаштовані джерела та змішування пристроїв.
5. Додати пороги застарівання, причини fallback і стійке відновлення, щоб випадковий один пакет не перемикав джерело кожен цикл. Для показу й для автоматичних рішень визначити окремі вимоги до повноти/часової узгодженості даних.
6. Відділити частоту отримання телеметрії, публікації станів, циклу HEMS і завантаження історії. Перехід на 2 секунди не повинен збільшувати частоту команд, навантаження на хмарні endpoint-и або вагу однієї доби в навчанні.
7. Зберегти хмарні добові лічильники окремо від локальних миттєвих потужностей. Не створювати другого лічильника тієї самої енергії. Повтори й зміна джерела не додають нові навчальні приклади штучно.

**Готовність:** перемикання джерела не змінює registry/історію; при розриві діє обрана політика; нулі не підміняють прогалини. Спочатку локальні значення порівнюються паралельно з production, потім підключаються до наявних сенсорів.

## Етап 5 Додати налаштування й діагностику

1. Розширити Config Flow та Options Flow пунктом «Джерело даних». Для наявного пристрою передбачити перевірку нового джерела, підтвердження збігу пристрою та просте повернення попереднього вибору.
2. У локальній гілці прибрати обов’язковий cloud login. В auto хмара використовується лише за наявності налаштованого доступу й дозволу fallback. Невідома прошивка отримує пояснення замість автоматичного вибору сумнівного профілю.
3. Показувати контрольні SOC, PV, навантаження, підтримувані поля, фактичний інтервал і стан зв’язку до збереження. Не вимагати введення регістрів, hex, credentials роутера або YAML для стандартного сценарію.
4. У діагностиці показувати джерело кожного поля, останнє отримання, відомий/невідомий час виміру, пропуски, версію профілю та причину fallback. Експорт діагностики очищати від секретів і приватних ідентифікаторів.
5. Додати українські й англійські тексти та перевірити авторизований UI. Локальне читання не оголошувати наявністю локального керування; недоступний канал команд має зрозумілий статус.

**Готовність:** користувач підключає і змінює джерело через налаштування тієї самої інтеграції, повертає хмару без перевстановлення й бачить причину недоступності полів. Перевірені нове встановлення та міграція наявного.

## Етап 6 Реалізувати перевірений шлях без OpenWrt

Перший кандидат — ESP32/RS232-шлюз із Home Assistant/MQTT підтримкою (наприклад, Solar2MQTT, для якого є користувацькі звіти саме про цю модель). Прямий RS232-USB до HA — альтернативний варіант, якщо підтримується транспортом хоста. В обох сценаріях RWB1 потрібно від’єднати або довести наявність окремого фізичного порту: один послідовний порт не обслуговують два активні master.

1. Спершу перевірити готовий ESP32→MQTT/HA шлях без зміни прошивки чи параметрів інвертора; зіставити доступні HA entities з canonical fields та перевірити freshness/units.
2. Якщо потрібна функція в самому плагіні, реалізувати провайдер читання підтверджених HA entities або MQTT-повідомлень, який не залежить від OpenWrt, з майстром зіставлення ID і контрольним тестом свіжості.
3. Перевірити реальний інвертор, відключення/повернення зчитувача та перезапуск HA. Виміряти частоту, похибки й доступні поля без вигаданих нулів. Лише якщо готовий міст не підходить, реалізовувати власний USB serial-provider.
4. Можливість зміни адреси сервера RWB1 та BLE перевіряти окремо; вони не є умовою першого релізу без OpenWrt.

**Готовність:** хоча б один повний сценарій без OpenWrt працює на реальному обладнанні та налаштовується через інтеграцію. Якщо бракує кабелю або доступу, назвати конкретний ресурс; RWB1-сценарій можна випустити окремо з чіткою вимогою до маршруту, без заяви про готову універсальну підтримку.

## Етап 7 Упакувати шлюз і випустити функцію

1. Постачати шлюз як необов’язковий HA App для HA OS і контейнер для Home Assistant Container. Пряме serial-підключення не потребує шлюзу або MQTT.
2. Зафіксувати сумісність версій інтеграції, шлюзу та профілів; healthcheck, мінімальні мережеві права, обмежений доступ до брокера й очищені журнали. Майстер має перевіряти встановлену версію.
3. Документувати чисте встановлення, оновлення, відмову, повернення на хмару й видалення. Для RWB1 початковий маршрут відновлюється перед зупинкою/видаленням шлюзу. Загальні інструкції не містять адрес і секретів власника.
4. Перевірити HA OS і Container, кілька пристроїв, cloud-only regression, локальну установку без cloud account, перемикання джерел, історію й lifecycle.
5. Після відповідних поведінкових перевірок виконати один повний runner на фінальному коді, commit/push, backup і поетапний deploy. Необхідний restart повідомляється перед виконанням; сам по собі цей план не забороняє restart.
6. Скласти таблицю моделей/прошивок із виміряною частотою й обмеженнями. Підтримку невипробуваних LAN/BLE-моделей не показувати готовою.

**Готовність:** чисте встановлення відтворюється за інструкцією; наявні користувачі залишаються на cloud-only до власного вибору; оновлення й повернення на хмару зберігають сутності та історію.

## Контроль роботи і межі цього плану

Порядок виконання: 1 → 2 → 3 → 4 → 5 → 6 → 7. Перевірки простішого локального інтерфейсу можуть змінити обраний транспорт, але не скасовують перевірку профілю, сталих ID, свіжості та відновлення.

Після кожного етапу фіксуються зміни, цільові перевірки, фактичні результати, версія коду й наступна дія. Проходження штучного тесту не дорівнює доказу роботи обладнання. Черговий етап у межах погодженого плану не потребує нового загального підтвердження; користувачеві повідомляється конкретна перешкода, якщо необхідний ресурс недоступний.

Реалізація розпочата у відокремленому worktree від актуального `origin/develop`; незакомічені файли основного каталогу збережені. Під час реалізації джерела лише читають дані; наявний захищений канал команд, ручні паузи та ліміти зберігаються. Adaptive, AI Shadow та outage observation не перемикаються довільно. Увімкнення live Assist або outage automatic залишається окремим рішенням користувача.

Після завершення телеметрії продовжуються якість історії, перевірка впливу режимів ШІ, точність PV, прогноз споживання й планування батареї за загальним планом. Прискорення отримання даних саме по собі не є доказом покращення прогнозу.

Реальну телеметрію не збережено у репозиторії; п’ять полів підтверджені попереднім пасивним зіставленням із HA.

**Залишок Етапу 1:** `decode_passive_observed_response` окремий від декодера корельованої відповіді, перевіряє адресу, функцію, довжину, CRC та межі; цільові тести перевіряють little-endian профіль і фрагментований MQTT. Один реальний Modbus-кадр раніше повністю збігся з п’ятьма сенсорами HA; байти кадру навмисно не збережено. Активний запит, стабільний інтервал публікації та пряма обробка збережених реальних байтів production-декодером ще не підтверджені. Локальний MQTT tap не можна підключати як достовірне джерело сенсорів. Наступна безпечна дія — перевірити RWB1 BLE/GATT або автентифікований локальний API лише якщо специфікацію/доступ можна встановити без зміни налаштувань; паралельно продовжити transport-independent інтеграцію й підготувати окремий hardware validation path для serial/ESP32. Serial reference підвищує впевненість у прямому RS232-кандидаті, але саме обладнання треба перевірити перед його підтримкою.

### Уточнення після незалежної перевірки handover

Деталі: [аудит RWB1 handover](rwb1-handover-audit-2026-10-19.md). 32/32 коротких replies з наданого логу мають стандартний Modbus CRC16; вони не містять register address і не доводять одиниці W. У логу є 17 пар однакових MQTT body з проміжком менше 0,15 мс, тому кількість рядків не є кількістю вимірів.

Власний capture analyzer раніше шукав лише великі блоки й довгі Base64 strings. Після виправлення він розпізнає 1..125-word replies та окремо read requests. Попередні слова «Modbus кадрів не знайдено» стосуються старого детектора й **не виключають коротких валідних replies**. Свіжий 40-секундний router capture показав 408-byte outgoing PUBLISH з 4 CRC-valid blocks (1/8/21/29 words) та 53-byte incoming PUBLISH. Read request з адресою регістру у цьому вікні не знайдено. Це підтверджує повніший payload і двосторонність, але ще не mapping та незалежність від cloud. Цільові тести після змін: **38/38 PASS**.

Отримані `mitm_*.py` не запускались: вони активно змінюють ARP, мають проблеми MQTT reassembly і декодування 7-byte frame. Подальше спостереження виконується через OpenWrt без ARP poisoning. Поточний наступний крок — встановити JSON paths та register mapping для знайдених blocks і виміряти каденцію повного набору.
