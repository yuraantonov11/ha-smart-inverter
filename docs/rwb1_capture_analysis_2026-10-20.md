# RWB1 passive capture — verified analysis with limitations

Дата аналізу: 2026-10-20. Аналізатор: `scripts/rwb1_analyze.py`
Тести: `tests/test_rwb1_analyze_round7.py` (12) + `tests/test_inspect_rwb1_mqtt_capture.py` (7) = 19/19 PASS.
Регресії round 7 закрито: per-field endianness, exact-second matching з трьома годинниками,
reassembly через межі ротації, категорізація пропусків, коректний `-C` в tcpdump.

## 2. Три годинники, які не змішуються

- `payload_ts` — поле `b.ts` у JSON від RWB1, формат `2026-10-20T10:45:07.000+08:00`.
  Декларований offset **+08:00**. Аналізатор застосовує його і переводить в UTC.
  Чи годинник пристрою реально синхронізований — **невідомо**; NTP-перевірки не було.
- `cap_ts` — час пакета в pcap (epoch, з роутера). Не залежить від годинника RWB1.
- `ha_ts` — `event_timestamp` циклу HA, UTC.

`TsStream.ts_at(offset)` повертає час саме того TCP-сегмента, де лежить
заголовок PUBLISH. Раніше всі спостереження мали `stream.first_ts` — це
помилка, виправлено.

### Причина 6 відкидань — не збій аналізатора

HA polling **деградував** у вікні 03:14–03:37 UTC. Цикл 5 с → **36 с**
(86 розривів > 7 с, зокрема серія 35.6 / 36.0 / 37.0 / 52.0 с). Тому в цих
секундах циклу HA просто немає:

|---|---|---|
| 02:50:07 | 02:50:12.508 | +5 с (поза ±2) |
| 03:15:08 | 03:15:02.683 | −6 с (поза ±2) |
| 03:20:09 | — | немає в ±8 с |
| 03:25:10 | 03:25:04.041 | −6 с (поза ±2) |
| 03:31:10 | — | немає в ±8 с |
| 03:36:10 | 03:36:18.684 | +8 с (поза ±2) |

Розподіл outcomes HA у вікні: fresh_success 483, empty_response 102,
timeout 28, malformed_response 18. **Це обмеження HA-полінгу, не capture.**

## 4. `-C 1048576` — одиниці

`-C file_size` у tcpdump/libpcap задає **мільйони байтів** (1 MB за замовчуванням).
`-C 1048576` ≈ 1 TB — тобто не обмеження. Ротацію робить `-G 600`.
**Єдиний реальний ліміт — guard-скрипт**, він лишається.

## 5. Покриття — три розділені категорії

- **Відсутність пакетів у pcap:** kernel drops не зафіксовано (tcpdump не
  друкує їх у `-w` без `-U` stderr). **Невідомо.**
- **MQTT/TCP reassembly:** `total_gaps = 2` — два розриви TCP-послідовності.
- **Відкидання декодером:** `decode_rejects = {}`, CRC валідний у 25/25.

Фактичні інтервали PS4Z (n=14):
- median **301 с**, p95 **601 с**, max **601 с**
- гістограма: 300, 301, 302, 358, 360, **601**

`601 с` — це **пропущений push**, не подвоєний інтервал: два сусідні інтервали
300 + 301 = 601. Тобто в 2 випадках із 14 push просто не дійшов.

Час працездатного capture: **77.1 хв** (`cap_ts` 1792482307.0 … 1792486931.7).
Повідомлень: **15**. При 300 с очікувалося ~15.4 — **дефіцит ≈ 0.4 push**.

Обчислення лише по вікну, де pcap реально містить дані: 02:45:07 → 04:02:12 UTC.

## 6. Що лишається невідомим

- Byte order для 25 RPC-регістрів (обидва трактування наведено, профілю немає).
- Одиниці й масштаб для SOC та PV power.
- `chargeSourcePrioritySetting` — відсутній у всіх 15 транзакціях. Немає доказів,
  що він polled; можливо write-only або поза діапазоном.
- Походження `SOC=100%` у HA: `cached=False` доводить лише відсутність
  локального кешу інтеграцією. `device_measurement_at` — 0/212 циклів.
- Чи 51.5 V (RWB1) і 58.1 V (HA) — різні точки вимірювання: **гіпотеза**,
  mapping не підтверджений.
- NTP-стан годинника RWB1.

Непідтверджені поля до HEMS **не підключені**. Режими RWB1 не змінювались,
фізичних команд не надсилалось.
