# Експериментальне локальне BLE-читання PowMr RWB1

Статус: **експеримент, opt-in, не для продукту.** Дата документа: 21 жовтня 2026 року.
Реалізація: `telemetry_sources/rwb1_ble_profile.py`, `telemetry_sources/rwb1_ble_codec.py`,
`telemetry_sources/rwb1_ble.py`. Жодна з цих частин не підключена до coordinator, не змінює
наявні сутності, історію чи cloud-налаштування. Жодних live-запитів не виконано.

## Рівень доказів (читати перш за все)

| Твердження | Стан |
| --- | --- |
| Протокол BLE (GATT, AES-конверт, фрагментація) читає відповідь інвертора | **підтверджено** — 2 успішні читання |
| Little-endian розбір 21-word блоку відтворює правдоподібні значення | **підтверджено** для тих самих 2 читань |
| Фізична звірка з дисплеєм інвертора / мобільним застосунком | **НЕ завершена** |
| `battery_soc`: 100 % (BLE) проти 95 % (cloud) | **НЕ підтверджено**, діагностичний кандидат |
| `load_power`: 301 W (BLE) проти 398 W (cloud) | **НЕ підтверджено**, діагностичний кандидат |
| Стабільність 30 хвилин / добу | **НЕ перевірено** |
| `battery_current` | **НЕ підтверджено, не змаплено** у профілі |
| Комунікація `CmdNo` повертається у відповіді | **не перевірено**; код вимагає збігу лише коли поле присутнє, і явно позначає відсутність |
| Робота через мережевий BLE-проксі (Xiaomi Gateway 3) на живому залізі | **НЕ перевірено**; лише тест із підставним bleakenector |

Два успішні читання — це доказ протоколу, а не доказ коректності полів. Розбіжність
SOC і load не пояснена: це може бути інший момент вимірювання, іншийregister-зсув,
або помилка карти. Поки це не звірено з дисплеєм, ці поля не можна вважати
телеметрією для керування.

## Виправлене хибне твердження про endianness

Завдання, що порушило цей інкремент, стверджувало: «`telemetry_sources/rwb1.py`
використовує big-endian і дає абсурдні значення». **Це хибно.** Перевірено
безпосередньо в коді: рядок 118 уже робить

```python
words = [int.from_bytes(response[3 + i * 2:5 + i * 2], "little") for i in range(21)]
```

тобто вже little-endian, і поле-map там уже збігається з наданим
(`words[1]`/`10`, `words[4]`, `words[5]`/`10`, `words[6]`, `words[12]`).
`rwb1.py` **не змінювався** (md5 `7d3c6719c8951c89dd0b1c99314cb7b0`, 5561 байт).

Натомість зроблено явний **версіційований** профіль із власним `profile_id`
(`rwb1-ble-fee7-21w-le-v1`), де endianness задокументовано явно, разом із картою
полів і рівнем доказу кожного поля. Це додатковий модуль, а не зміна наявного
decoder-а: старі `profile_id` (`…-experimental-v1`, `…-passive-candidate-v1`)
лишаються без змін, щоб раніше записані кадри залишалися інтерпретованими.
Регресія проти silent-swap назад у big-endian зафіксована тестом
`test_big_endian_reading_of_the_same_block_would_be_absurd`.

## Протокол

**Дозволений запит — рівно один.** `05 03 11 95 00 15 90 91`
(slave 5, function 03, start 0x1195, count 21). Відповідь — рівно 47 байтів,
`response[2] == 42`, CRC16 Modbus валідний, slave/function збігаються.
Керування, записи конфігурації, pairing і перебір регістрів **не реалізовані**
в жодному модулі: `build_allowlisted_request()` не приймає жодного аргументу,
а `validate_allowed_request()` приймає лише побайтовий збіг із allow-list.

**Конверт.** Ключ `MD5((DTU_ID.strip() + "SEC_").encode()).digest()` (16 байт),
AES-128-CBC з IV == ключ, компактний JSON, zero-pad до кратного 16, base64.
Запит: `{"CID":30024,"PL":{"Req":<HEX>,"Uart":{2400,8,"NONE",1},
"CmdType":"gatherSingleDevProps","CmdNo":<4 alnum>}}`.
Відповідь очікує `CID 30025`, `RC 0`, `PL.Rsp` = Modbus HEX.

**Фрагментація** — приватна 3-байтова: `index` (з 1), `total`, `length`, далі
payload; chunk ≤ `min(227, MTU-6)`.

**GATT** (handle визначаються discovery, не фіксуються):
service `0000fee7-…`, write `0000fed5-…`, indicate `0000fed6-…`, CCCD `0x0002`.

## Карта полів профілю `rwb1-ble-fee7-21w-le-v1`

| Word | Поле | Масштаб | Рівень доказу |
| --- | --- | --- | --- |
| 1 | `grid_voltage` | /10 | зіставлено з cloud |
| 4 | `pv_power` | ×1 | 2 BLE-читання, не підтверджено |
| 5 | `battery_voltage` | /10 | зіставлено з cloud |
| 6 | `battery_soc` | ×1 | 2 BLE-читання, **не підтверджено** |
| 12 | `load_power` | ×1 | 2 BLE-читання, **не підтверджено** |

`battery_current` свідомо **не** змаплено. Значення поза фізичним діапазоном
стають `None` з `quality=UNKNOWN` — **ніколи** нулем. `measured_at` завжди
`None`: пристрій не передає час фізичного вимірю, лише час прибуття кадру
(`received_at`).

## Реалізація й обмеження

**Codec** (`rwb1_ble_codec.py`) перевіряє: base64 (`validate=True`), довжину
% 16, `CID == 30025`, `RC == 0`, наявність і парність `PL.Rsp`, `CmdNo`
(збіг вимагається **лише якщо поле присутнє**; відсутність приймається й
позначається `cmd_no_present=False`). DTU ID живеє тільки в пам'яті, не
логується і не пишеться на диск; `repr` провайдера не містить ані DTU ID, ані
ключа, ані BLE-адреси.

**FragmentReassembler** відкидає: index == 0, total == 0, index > total, total
понад адресовний діапазон, `length`, що не збігається з chunk, oversize
payload, конфліктний дублікат (той самий index з іншим payload) і зміну total
посеред message. Ідентичний повтор приймається як ретрансляція. Неповний
 reassembly завершується timeout-ом, а не мовчанням.

**Transport** (`rwb1_ble.py`) реалізує `TelemetryProvider`:
одна активна транзакція (`asyncio.Lock`), обмежені часовіouts, reconnect з
експоненційним backoff, `stop_notify` + `disconnect` на `close()`/unload,
мінімальний інтервал **не частіше 5 секунд** (конструктор не приймає менше).
bleakenector інжектується і має вузький BleakClient-подібний интерфейс
(`connect`/`disconnect`/`write_gatt_char`/`start_notify`/`stop_notify`/`services`/`mtu_size`),
що робить transport тестованим із fake. Типовий клієнт — `BleakClientWithServiceCache`
через Bluetooth API Home Assistant (це потрібно для мережевих проксі на кшталт
Xiaomi Gateway 3); `aioesphomeapi` **не** імпортується напряму, `bleak` імпортується
ліниво.

## Жорсткі гейти: enforced-політики (2026-10-21)

Навіть коли `SourceMode.BLE` увімкнено через явний opt-in, BLE не може
підняти в керування поле без доказу. Це досягається двома незалежними gates:

1. **`FieldPolicy.allowed_providers`** у `telemetry_sources/selection.py`.
   Поле без `allowed_providers` лишається повністю відкритим (зворотна
   сумісність); будь-яка непорожня множина обмежує джерела для цього поля
   як остаточний gate після перевірок `receipt_age`, `measurement_age`,
   `quality` і `value`. Відхилення пишуться в `excluded[name]` з причинами
   типу `rwb1_ble: provider is not allowed for this field` — оператор
   бачить, хто заблокований і чому.
2. **`SourceMode.BLE`** у `telemetry_sources/settings.py`. Опція:
   * потребує `experimental_ble_consent: True`,
   * не приймає `collector_id == "powmr_cloud"` і не приймає порожні/пробільні ідентифікатори,
   * `provider_order` **завжди** повертає `(powmr_cloud, rwb1_ble)` —
     cloud перший, BLE ніколи не стоїть першим, навіть коли `cloud_fallback=False`,
   * перевірка суворої булевості (без `bool("true")`-когоерсії).

Точний набір політик визначає `telemetry_sources/ble_policies.py::ble_policies()`.
Він прив'язаний до рівня доказів, зафіксованого вище:

| Поле             | Дозволені провайдери | Доказ                                                                 |
|------------------|----------------------|-----------------------------------------------------------------------|
| `grid_voltage`   | `powmr_cloud`, `rwb1_ble` | зіставлено з cloud: 232.0 V (BLE) vs 231.8 V (cloud)            |
| `battery_voltage`| `powmr_cloud`, `rwb1_ble` | зіставлено з cloud:  58.1 V (BLE) vs  57.8 V (cloud)            |
| `pv_power`       | `powmr_cloud`        | 2 BLE-читання, не підтверджено (той самий клас, що `battery_soc`)    |
| `battery_soc`    | `powmr_cloud`        | 100 % (BLE) vs 95 % (cloud), не звірено з дисплеєм → BLE заблоковано |
| `load_power`     | `powmr_cloud`        | 301 W (BLE) vs 398 W (cloud), не звірено → BLE заблоковано          |
| `battery_current`| — (немає політики)   | не змаплено в `rwb1_ble_profile.FIELD_MAP`; рішення відкладене       |

`pv_power` тут свідомо заблокований для BLE, хоча належить до
«2 BLE-читання, не підтверджено» — той самий клас, що `battery_soc` і
`load_power`. Він би впливав навіть на діагностичні звіти PV, тому
консервативний gate однаковий.

Звідси випливає, що **BLE не може підняти SOC/load у керування**: навіть якщо
ввімкнено `SourceMode.BLE`, виклик `select_fields` відкидає BLE-кадри з
тими полями ще до того, як їх побачить `select_fields.sources`. Увімкнення
BLE дозволяє лише підтверджені поля (`grid_voltage`, `battery_voltage`)
стояти поряд із cloud; для непідтверджених полів BLE лишається лише
діагностичним кандидатом, а не джерелом, що живить HEMS.

`battery_current` не має політики у `ble_policies()`. Це свідома відсутність,
а не забування: на момент написання це поле не змаплено у
`rwb1_ble_profile.FIELD_MAP`. Коли з'явиться перша звірена capture, додайте
політику з тим самим `allowed_providers` за результатом зіставлення з cloud.

## Перевірки, які виконано

104 синтетичних тести (26 профіль + 47 codec + 31 transport) — усі проходять;
жодного реального MAC/IP/DTU ID/ключа/конверта у fixtures. Перевірено:
endian-регресія; фрагментація (розміри, границі, дублікати, конфлікти, oversize,
incomplete, out-of-order); crypto round-trip, неправильний ключ, битий base64,
некратна-16 довжина, CID≠30025, RC≠0, відсутній `PL.Rsp`, непарний hex;
CRC (включно з відомим вектором `modbus_crc16(b"123456789") == 0x4B37`);
allow-list (відхилення інших register/function/slave/count); transport із fake
bleakenector (успішне читання, timeout, cleanup, reconnect/backoff, конкурентний
lock, `CmdNo` присутній/відсутній). Наявні тести телеметрії (37) не зламані.

Плюс 32 нових синтетичних тести для enforced-політик
(8 FieldPolicy + 15 SourceMode.BLE + 9 ble_policies) — усі проходять; з них
8 перевіряють, що BLE-policies не можна випадково послабити, і жоден не
використовує реальних MAC/IP/DTU ID/ключів. Загалом телеметричний пакет
нараховує 182 тести, всі зелені. Під час реалізації тести виявили три
реальні дефекти в новому коді, які виправлено:
порожній список повідомлень є falsy (callback глушив усі фрейми); стан транзакції
не ініціалізувався до `connect()` ( unsolicited-кадр під час connect дав би
`AttributeError`); перевірка total виконувалася до скидання стану на `index == 1`.

## Що НЕ перевірено

Фізична звірка з дисплеєм; стабільність 30 хв / добу; `battery_current`;
реальна робота через мережевий BLE-проксі; поведінка пристрою при
повторному запиті частіше ніж 5 с; поведінка за межами 2 успішних читань.
Жодного live BLE-запиту не виконано.

## Наступний крок

Фізична звірка полів із дисплеєм/застосунком на одному readings-вікні (зокрема
`battery_soc` і `load_power`), потім безперервний прогін 30 хвилин із записом
лише агрегованих показників. До завершення цієї звірки профіль не можна
піднімати вище за «діагностичний кандидат», а `battery_soc`/`load_power` не
можна використовувати для керування.
