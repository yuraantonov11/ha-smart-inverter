# Прогнозна допомога HEMS · Phase 1

AI працює поверх Adaptive / Arbitrage / Storm. Власник обирає режим
прогнозної допомоги через наявний select **Off / Shadow / Assist**.
Інтеграція сама не вмикає Assist.

## Рекомендація та застосування

Планувальник використовує виміряну історію погодинного споживання,
прогноз PV, тарифи та ємність батареї. Він формує SOC-цілі, нічне
вікно, поточні output/charger priorities та план наступних 24 годин.
Це локальний числовий планувальник без зовнішньої LLM або нових залежностей.

У Shadow рекомендації доступні для перегляду; рішення інвертора залишаються
базовими. В Assist застосування можливе лише за `samples >= 3` і
`confidence >= max(0.2, predictive_min_confidence_for_assist)`.
Порожній калібратор, недостатня впевненість або відсутній план означають baseline.

`PredictiveControlEngine` розширює прийнятий HEMS engine: пропозиція
вибирається перед наявною фільтрацією команд. Ручний контроль, circuit breaker,
невалідна/застаріла телеметрія, reserve SOC, мінімальний робочий SOC,
відновлювальний hysteresis, захист вечірнього резерву, dwell/dedup,
keepalive та STORM мають пріоритет. Інтеграція не змінює обмеження BMS.
При відсутній мережі AI не підміняє рішення базового HEMS.

Сенсор **Predictive Decision State** додається до пристрою інвертора:
типова назва для пристрою «Гараж Smart Solar Inverter» —
`sensor.garazh_smart_solar_inverter_predictive_decision_state`.
Фактичний entity ID визначає Home Assistant (перевірте реєстр сутностей).
Існуючі entity IDs не перейменовуються.

Атрибути: `mode`, `output_priority`, `charger_priority`, `target_soc`,
`reason`, `execution_reason`, `confidence`, `samples`, `applied`,
`override_pending_until`. `reason` описує рекомендацію, `execution_reason` —
фактичне рішення/блокування. `applied=true` означає, що необхідні записи
підтверджені API або поточні прочитані priorities вже відповідають пропозиції.
Це не незалежне підтвердження фізичного перемикання після запису.
Помилка доставки або заблокований dwell не позначаються як застосування.

Сенсор Predictive Day-Ahead читає актуальний план із engine, а не з
неіснуючого поля coordinator. Його поточний ID зберігається.

## Навчання й калібрування

Модель станції навчає коефіцієнт перетворення сонячної радіації на PV
за повними історичними днями. `learned_pv_ratio` не є впевненістю.
Прогноз на майбутню дату записується до появи факту. Після завершення дня
повний виміряний PV-факт утворює одну пару з цим прогнозом.
Пари зберігаються атомарно у per-entry JSON, а використані дати не дублюються.
Жодні синтетичні пари не створюються для відкриття Assist.

Калібратор показує кількість пар, MAE, bias і впевненість.
`bias = actual - forecast`; у денному калібраторі це kWh, попри історичний
суфікс `_w`. Модель станції та цей калібратор виконують різні функції.
Поріг у три пари не гарантує достатню впевненість: потрібно накопичити
достатньо точних прогнозів. Корекція прогнозу має власний поріг у чотири пари.

За п'яти або більше пар і `-bias / mean_forecast > 0.3` планувальник
рекомендує обережність через систематичний дефіцит PV. Це не доказ грози.
Рекомендація USB + SNU може діяти тільки в Assist, з достатньою впевненістю
та ввімкненою користувачем опцією `auto_storm_by_forecast`.
Обраний smart mode не переписується; STORM ніколи не послаблюється.

## Чи прискорює історія сервера навчання?

Клієнт API має `fetch_history(start, end)` для історичних вимірювань і
`fetch_monthly_energy()` для добових PV-фактів. Ці дані можуть прискорити
навчання споживання та станційного gain, якщо локальної recorder-історії бракує.
Pipeline використовує recorder-історію, а добові cloud-PV-факти заповнюють
її прогалини. Імпорт місячних звітів охоплює останні 120 днів (максимум
п'ять місяців) і повторюється не частіше разу на добу. Приймаються тільки
`pvGeneratedEnergy`, одиниці `kWh` і `isRealValue=true`; поточний день та
майбутні дні відкидаються. Recorder має пріоритет. Для облікових записів
із кількома інверторами імпорт вимкнений: owner overview не має перевіреного
вибору конкретного інвертора.

Перевірка сервера 2026-10-03: endpoint сирої історії повертає HTTP 404,
а місячний PV-звіт доступний. Тому погодинне споживання залишається
з recorder; недоступна cloud-історія не підмінюється добовими середніми.

У поточному API-клієнті немає методу для архіву прогнозів, випущених до
відповідного дня. Самі історичні PV-факти не замінюють real forecast pairs.
Для скорочення очікування калібратора потрібні збережені наперед прогнози
з датою випуску та відповідні факти. Прогноз, побудований заднім числом,
можна використати для окремої перевірки моделі, але не як live calibration pair.
Тимчасовий перегляд доступний у Shadow без штучного підвищення впевненості.

## Feedback

Сервіс `powmr_inverter.predictive_feedback`:

```yaml
action: reject
duration_min: 60
# entry_id: ваш_config_entry_id
```

`reject` ставить ручну паузу HEMS. Інтеграція не посилає команд priorities
під час цієї паузи. `modify` задає ціль, видиму як pending, і таку саму паузу:

```yaml
action: modify
new_target_soc: 75
duration_min: 30
```

Під час паузи ціль не обходить ручний контроль. Після закінчення паузи
тимчасова ціль знімається і використовується новий план. `approve` тільки
логує підтвердження; він не скасовує паузу та не вмикає Assist.
Пауза і pending SOC зберігаються в `entry.options`; прострочена пауза
після рестарту не відновлюється. Коротший feedback не скорочує вже
активну ручну паузу. Для кількох інверторів обов'язково вкажіть `entry_id`.
Feedback не є виміряною PV-парою і не збільшує calibration samples.

Старі неактивні дії feedback замінено на approve/reject/modify;
оновіть автоматизації, якщо вони використовували попередні назви дій.

## Налаштування та dashboard

Початкова конфігурація та options показують:
`predictive_default_mode` (Shadow), `predictive_night_window_start_hour` (23),
`predictive_night_window_end_hour` (7),
`predictive_min_confidence_for_assist` (0.2).
Початковий режим застосовується при створенні інтеграції; збережений
`predictive_mode` має пріоритет над default. Поточний режим змінюється
через наявний select. Поріг можна підвищувати; нижче 0.2 керування не відкривається.

У `dashboard.yaml` є стан/причина, лічильник реальних пар і кнопки
«Підтвердити», «Скасувати на 30 хв» і select «Скоригувати SOC» (20–100).
Вибір SOC ставить ручну паузу на 30 хвилин і показує pending ціль.
YAML — шаблон; його entity IDs потрібно зіставити з вашою інсталяцією.
Наявний dashboard у Lovelace storage не перезаписується автоматично.

## Логи

Формат (числа нижче є прикладом, а не доказом живого застосування):

```text
Predictive applied: mode=Assist conf=0.35 n=12 applied=SBU charger=OSO reason=[ML] ...
Predictive feedback: action=reject duration_min=60 target_soc=None
Real pair captured: date=2026-10-03 fc=5.0kWh ac=3.0kWh delta=-2.0kWh
```

Live-перевірка після встановлення потребує перезапуску HA та перевірки
свіжих логів і сутностей. Git push сам по собі не встановлює зміни в HA.
